# 候选身份、证据与推荐

## 候选结构

`merge` 和 `rank` 接受候选数组，或包含 `candidates` 的对象。每项至少有非空 `name`；Agent 提取候选时同时提供实际来源链接。以下是字段说明，具体空白模板位于 `assets/assessment.example.json`。

| 字段 | 含义 |
| --- | --- |
| `origin.repository`, `origin.path` | 实际仓库与 SKILL.md 相对路径；未查明为 `null` |
| `origin.ref` | 真实分支或发布引用；不同引用在对应关系明确前不合并 |
| `origin.registry`, `origin.publisher`, `origin.slug` | 独立注册表的发布身份 |
| `origin.directory` | 用户明确提供的本地目录 |
| `listings[]` | `source`, `url`, `observed_at`，保留每个发现位置 |
| `metrics[]` | `source`, `kind`, `value`, `scope`, `url`, `observed_at`；认可度和使用量优先记录 `stars`、`favorites`、`bookmarks`、`saves`、`likes`、`installs`、`downloads` 及周/月指标 |
| `verification` | 上游核验状态、范围与证据 |
| `assessment` | 功能组、必要条件判断和四维评估 |

目录站的指标、介绍与安全扫描是证据输入，不能自动把 `verification.status` 设为 `verified`。

已读上游后，填写例如 `verification.status: verified`，并在 `evidence` 列表记录 SKILL.md、安装说明、资源树等实际 URL、文件路径、核验范围与观察时间。没有执行安装或行为验证时，在核验记录中明确这一范围。

关键条件的证据记录要指向实际保存的原文或工具响应，格式和响应命名见 [证据与覆盖核对](evidence.md)。只有链接或自己撰写的概述不足以支持必要条件已核实。

## 去重

- 仓库来源：规范化仓库地址与真实文件路径；保留分支差异。
- 注册表来源：注册表地址、发布者与 slug，不能只看 slug。
- 本地来源：实际目录。
- 路径未知：保留目录站身份。多次观测同一目录条目仍是一个候选，指标观测分别保留。
- 不同作者、fork、派生修改及相似用途保留独立项。
- `unverified` 与 `verified` 合并可正常升级；重复核验的时间、范围或证据差异不作为冲突。
- 合并后的 `verification.records` 保留原始观察，顶层 `evidence` 合并已核验记录的证据。重复输入不增加重复记录，嵌套合并不生成历史树。
- 可选 `verification.facts` 使用同一字段的规范化结论，例如 `{"platform": "macOS", "license": "MIT"}`；未知为 `null`，不会抵消已知事实。两份已核验记录的同一字段存在不同非空值时，标为 `conflict`，列出 `conflicting_fields`，不选择其中一个值。不同提交/时期的结论先由 Agent 明确适用范围，不能靠观察时间自动覆盖。
- 脚本不推断文字语义：原文实质矛盾由 Agent 标记 `status: conflict` 并提供理由和证据。显式冲突合并后仍保留，移除评估，暂不推荐。
- 同源出现不同 `assessment` 时保留 `assessment_variants` 并暂停评分，避免输入顺序决定是否符合条件。即使只因表述不同，也由 Agent 综合核对后生成一份当前评估。
- 解决冲突时，用重新核验的单份候选替换待比较输入中的旧候选：保留必要原文证据，清除已解决的旧 `records`、`verification_variants`、`assessment_variants`，填写当前结论及理由；不要把新记录和未解决旧记录一起交给 `merge`。旧文件可保存在任务证据目录，脚本不自动裁决冲突。

脚本不合计多个网站的下载或安装量，也不挑一个更大的数字冒充总安装数。同一指标多次观测时保留原记录，评估使用当前、可核对的记录并注明时间。

## 评估

先设置 `assessment.group` 为实际用途，例如 `personal-wechat` 或 `official-account-publishing`。同一次请求可展示多个组；推荐名次只在同组内解释。

设置 `eligible`：

- `true`：已核对用户必要条件，可以比较。
- `false`：不满足已明确的条件；提供 `exclusion_reason`，例如平台不支持或许可禁止用户用途。
- `null` 或未填写：尚不明确，进入待核验列表。

每个已知维度使用：

```json
{
  "score": 4,
  "reason": "基于实际核验写出具体理由",
  "evidence": [
    {"url": "实际上游或指标页面地址", "quote": "相关证据"}
  ]
}
```

上例仅说明格式，不是对任何真实 Skill 的打分。未知维度直接使用 `null`；不能把未知写成零分或用搜索摘要补造事实。

| 维度 | 0–5 判断重点 |
| --- | --- |
| `fit` | 0 不支持；1–2 只能完成外围任务；3 支持核心但有明显缺口；4 满足核心用途；5 明确覆盖所需流程及边界 |
| `popularity` | 必须引用原始 `metrics[]` 中的 star、收藏、安装或下载信号；优先同一平台、同一指标和相近统计时间的相对判断，并说明所用群体、统计范围、原始数值和观察时间，证据不足保持未知 |
| `maintenance` | 看相关文件和共享依赖的更新、持续维护、发布与缺陷响应；判断变化是否有意义，稳定成熟不因少更新自动低分 |
| `quality` | 看安装说明、资源完整性、依赖与适用边界是否足以复现；只阅读说明不能宣称已验证运行效果 |

`popularity` 不按固定“一千安装”门槛淘汰新项目。不跨平台机械换算安装量；仓库星数只作为仓库级辅助。`maintenance` 不把整个集合仓库的最新提交当成员最新更新，也不把网站重新抓取时间当作者发布。

## 计算与解释

默认权重为功能 45、社区认可度与使用量 25、维护 20、安装说明完整性 10。自定义权重必须包含全部四项、为正有限数，脚本归一化到百分比。

已知维度贡献为 `权重 × 等级 / 5`。缺失维度的贡献区间为 `[0, 权重]`：

- 全部已知：输出辅助 `score`。
- 部分未知：`score` 为 `null`，输出 `score_range`、未知维度和已知证据权重占比。
- 区间只是缺失信息的数学边界，不是测量误差、预测概率或统计置信区间。
- 按区间下界提供保守展示顺序；区间重叠时顺序暂定，需要解释取舍，必要时补齐证据。
- 不跨功能组判定唯一赢家；有待核验项、来源缺口或首项指标不完整时不宣称唯一最佳。

用户有特殊偏好时调整权重，必要条件仍先判断，不能靠热度抵消平台或许可证不兼容。

## 报告

展示约三项推荐，通常包括：

1. 名称、作者、实际功能及推荐/备选定位。
2. 原始热度数据：至少列出可取得的 star、收藏、安装量或下载量，连同指标来源、作用范围和观测时间。
3. 相关维护证据、前置条件、许可证和安装范围。
4. 推荐理由、证据缺口、上游链接及核实过的安装方式。

同时报告已查询来源、失败与替代方法。没有足够已核验候选时交付发现结果和具体缺口；不要把待核验条目伪装成安装推荐。
