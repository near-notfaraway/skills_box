# 证据与覆盖核对

证据用于核对推荐理由。复用已取得的原文，只留与结论有关的材料，存于任务临时目录或用户指定的本地位置。

## 关键条件

每个进入正式推荐的候选，检查核心功能、平台、运行依赖、账号/激活、费用、许可证和安装单元。可以在候选 JSON 的 `verification.evidence` 中记录：

```json
{
  "url": "实际读取的上游 URL",
  "observed_at": "实际观察时间",
  "artifact": "evidence/request-001.txt",
  "quote": "原文中的相关句子",
  "supports": ["platform", "activation"]
}
```

路径相对于本次结果目录，文件应含实际取得的原文或工具响应；HTML/JSON 同样可用。`quote` 逐字摘录，翻译或推断写入另外的理由中。没有必要机械填满所有字段，但复核者必须能从结论找到原文和来源。脚本只合并这些记录，不会验证文件内容是否支持结论。

- 许可文本优先于仓库标签或目录站说明；标签只支持“该站声明某许可证”。
- README 描述功能，实际脚本帮助确认限制；只读源码不能称为已验证运行成功。
- CLI 不存在要有实际探测结果；未运行不能写成缺失。
- 原文读取失败时保留失败状态。只有搜索摘要或执行者概述时，关键条件仍未知；不能因附了 URL 就标已核实。
- 对“主流、好用、被认可”的结论，至少保留一条原始热度证据；优先包含 GitHub star、收藏/书签数、Skill 安装量或下载量。记录指标的对象范围（仓库或 Skill）、统计窗口和观察时间，不能把不同范围的数字相加。

## 响应命名

使用请求序号或 URL 哈希生成不冲突的响应文件名，并保留 URL、方法、状态、观察时间和文件位置；需要校验完整性时附 SHA-256。

不同大小写 URL、不同重试或替代路径各自保存。例如 `REFERENCE.md` 的失败响应和 `reference.md` 的成功响应不能在大小写不敏感文件系统上共用名称。后续成功不会覆盖前一次错误记录。

## 候选覆盖

按用户核心任务填写“满足／不满足／未知”，必要时注明需要适配。以“提表＋合并＋拆分”为例，只有三项都有原文支持才是完整候选；只提供版式复核的 Skill 属于补充工具。

首轮结果受关键词、每源条数上限和目录排序影响，不代表候选全集。即使已经命中完整候选，也先按主流程完成高信号名称的精确反查和准确度门；不能因为“已有三个可用候选”就跳过可能改变首选的名称实体扩展。之后优先核验满足条件的上游，不继续围绕热门但不满足条件的候选反复查资料。达到预算仍不足时报告缺口，不用部分功能凑足三项。

为每个高信号候选区分并记录：

- 对外展示名或社区俗称；
- 市场安装 slug；
- `owner/repo` 与仓库名；
- 实际 `SKILL.md` 路径和 frontmatter `name`；
- 证明这些名称属于同一上游的原文。

目录中的近似名称不能互相替代。某个 `ui-taste` 上游无法核实时，结论只能针对该发布者和 slug，不能扩大成“没有可核验的 Taste Skill”；同理，译版、fork 或搬运版本不能冒充原始上游。

## 来源状态

同一来源的每种方法分别记录，例如 API 鉴权失败、公开页面取得两项候选。全文读取器的短摘要不代表原始响应没有内容；先检查已保存 HTML 的候选链接、JSON 的结果数组。

最终覆盖说明与所有相关响应核对：有候选时报告发现数量、名称实体扩展及核验范围；确实没有匹配时只说明本次查询无匹配；失败时说明失败方法与是否完成替代。任何一种都不等于全站遍历。关键来源未覆盖或高影响名称仍有歧义时，排序标为暂定。
